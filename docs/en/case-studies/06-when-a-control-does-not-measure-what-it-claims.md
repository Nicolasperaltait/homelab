# Case 06 - When a Control Does Not Measure What It Claims To

## Context

Over a week of hardening a small production-grade lab platform, changes were made
to access, privilege, auditing and network filtering. Every change shipped with a
script that verified its own result.

**The most frequent pattern of that week was not a change that failed. It was a
verification that lied.**

It appeared seven times. It is worth writing down because it is not an
implementation slip: it is a reasoning error, and it recurs.

## The cases

### 1. The hardening that reported success without hardening anything

A script disabled password authentication and confirmed it had written the file
correctly. It had. **And passwords still worked.**

In that remote access service **the FIRST occurrence of each directive wins**,
and configuration fragments load in alphabetical order. A file generated by
automated provisioning, with a lower numeric prefix, was beating the hardening
one.

**The script verified that it had written, not that the system had changed.**

Fix: the fragment now loads first, and verification queries the service's
**effective configuration** instead of reading the file.

### 2. The guard that never checked anything

Before removing a disused account, a script counted files, processes and
scheduled tasks to confirm it was inert.

The counting utility **prints zero and reports failure at the same time**. The
defensive form in use produced two lines instead of a number, the numeric
comparison failed, **and a failing comparison reads as negative**. The conclusion
"it is inert" was produced without checking anything.

**A guard that fails permissive is worse than no guard**, because it produces a
claim nobody questions again.

Fix: normalise the counters and **block explicitly** when the value is not
numeric.

### 3. The verification that reverted a correct change

After applying a new credential to a service, the check looked for errors in the
container log. It found one and reverted the change.

**The error was hours old.** The check read the whole log, without scoping to the
restart that followed the change.

Fix: the source of truth becomes **the effective value in the process
environment**, compared byte for byte. The log stays informational, scoped to the
new start.

### 4. The security banner that broke automation

A restricted-access notice was added, as the hardening benchmark asks.

That notice **is emitted before authentication, on every connection**, including
non-interactive ones. Every automated command began returning seven lines of
warning mixed into its output.

**The control worked exactly as specified. The problem was its scope.**

Fix: an explicit exception for automation accounts.

### 5. The safety net that caused the very damage it rescued from

While preparing a network filtering change, a rescue timer was designed: if the
operator lost access, the rules would revert on their own after fifteen minutes.

**The rescue command flushed ALL filtering tables on the host**, not only its
own. On a container host that means the container network and every published
port. On the remote-access node, the entire tunnel.

**The rescue would have caused exactly the same damage as the failure it was
rescuing from.**

Fix: create, delete and recreate **only the owned table**. Nobody had checked
what the rescue command does on a container host: the safety net had been
written, not tested.

### 6. The validation that passed per piece and failed as a whole

A script generated two permission files, one per automation account, validating
each before installing. Both validated.

**The set did not.** Both defined the same alias, and defining an alias twice is
an error.

**Validating the piece does not validate the whole.**

And the worse mistake was elsewhere: **on detecting the problem, the script
warned and exited, leaving the broken files in place.** Another script written
the same morning did roll back.

**Warning is not rolling back.** A script that detects it broke something and
does not undo it is worse than one that never noticed, because it creates trust
in a check that does not protect.

### 7. And the inverse: the control that cried wolf on a healthy system

While deploying system auditing, the check reported that one host had loaded only
eight of twenty-three rules.

The host was investigated. Everything was fine.

**The cause was the check itself.** It waited a fixed interval and then counted.
Rules load one at a time, and on the slowest host that interval captured the load
**halfway through**. The eight were **the first eight in the file, in order**: the
clue was in the result all along.

**A control that reports failure on a healthy system is as defective as one that
stays silent during a real failure**, and worse over time: it trains people to
ignore it.

Fix: wait for the count to **stabilise**, and distinguish "may still be loading"
from "failed".

### 8. The sanitisation that only looked at the working tree

**Found on 2026-08-29, and it is the most uncomfortable case because it concerns
this very repository.**

This public repository has a documented sanitisation policy, with a list of
sensitive patterns and a mandatory scan. The scan was run against drafts and
against the diff before each commit.

**It was never run against history.**

Months earlier, a commit removed the environment's internal naming from the
working tree. The earlier commits kept it, and those commits **were already
published**.

The result: the working tree was clean, the scan passed, and the repository
displayed a "sanitized" badge that **was true of the tree and false of the
repository**.

**Same pattern as the seven previous cases: the action was verified -this commit
is clean- instead of the effect -the repository is clean-.**

Fix:

- history rewritten, with sensitive values replaced by explicit redaction
  markers, so an old commit plainly says it was sanitised rather than pretending
  it never said anything else;
- a verified backup of the full repository before touching anything;
- **the check now walks every object in every commit**, not just the diff of the
  change being made.

**Honest severity:** what was exposed were internal name suffixes, not routable
and worthless on their own. The real cost was not technical: it was the gap
between what the repository claimed about itself and what it did.

### And the first fix was incomplete too

**History was rewritten twice on the same day.**

The first pass covered the internal naming and **left seven product names
untouched**. The reason is the same defect once more: **the replacement list came
from the preliminary scan, and that scan only looked for what was already
suspected.** The fix inherited the blind spot of the search that defined it.

It was caught by verifying **against the remote** after publishing, not against
the local copy. A push completing successfully does not prove that what was
published is clean.

The second pass changed the method: instead of searching for a list of suspected
terms, **what was actually there was enumerated** -every phrase matching the
hedging pattern the repository used, plus a broad sweep of infrastructure product
names- and only then were the replacements built.

**Searching for what you suspect finds what you suspect.** To know what is there,
you have to enumerate.

**Severity, again without dressing it up:** product names are not sensitive data;
knowing someone's stack opens nothing. What was wrong was the inconsistency
between what this repository states -that it does not name products- and what its
history showed.

### And the check on the fix was wrong too

The first verification that history was clean used a shell pipeline where **the
exit status came from the last command rather than from the search**. It reported
matches on an empty result.

It was redone by measuring the content instead of the exit status, and a second
independent check was added over every object in the repository.

**Even the check on the fix needed checking.**

## The pattern

All seven are the same error in different clothes:

**The action was verified instead of the effect.**

- the file was written -> no: did the effective configuration change?
- the command returned success -> no: does the system now reject what it should?
- the piece validates -> no: does the set validate?
- the expected time elapsed -> no: did the operation finish?

## The practice that came out of it

Every script in this environment **checks what has to FAIL**, not only what has
to work.

| Control | What it checks fails |
|---|---|
| Privileged read wrapper | That it **denies** the password file, a private key, the host key, and a `..` path attempting to evade it |
| Privilege reduction | That a generic reader and a command interpreter **are denied** |
| Credential rotation | That the **old credential returns 401** |
| Remote access hardening | The **effective** configuration, not the file written |

The rotation case proves itself. The check has two halves: that the new
credential works, and that **the old one stops working**. On the first run the
new one worked and **so did the old one**.

**A script verifying only the first half would have reported "rotation complete"
with the exposed credential still valid.**

Creating a new credential is not rotation. **Rotation is the old one ceasing to
work**, and that has to be checked.

## Corollary: error messages are a control too

One script reported *"the permission set is invalid"*, which was **true**. It was
read as *"the system has lost privilege escalation"*, which was **false**: rules
were still being applied and only warnings were emitted.

The "obvious" recovery from that message was **restoring the checkpoint of a
machine that was working fine**. The real fix was two lines.

**An error must describe the extent of the damage, not only its existence.**
